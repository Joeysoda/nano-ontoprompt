# OntoFlow：不同行业/业务数据怎么落地（交付模式）

> 日期：2026-10-23 · 来源：OntoFlow + AbutionGraph 技术与应用白皮书（31 页 PDF，用户提供）；OntoFlow GitHub README · 证据等级：第三方厂商自述；从截图推测的写“本项目推断”
> 原件：[`evidence/ontoflow-whitepaper/`](evidence/ontoflow-whitepaper/)、[`evidence/ontoflow-github-readme-2026-10-23/`](evidence/ontoflow-github-readme-2026-10-23/)（不进 git，见 [`../ORIGINALS.md`](../ORIGINALS.md)）
> 白皮书文字层是乱码，靠逐页渲染成图片阅读，页码按 PDF 页序。

## 一句话结论

**通用平台 + 厂商（或合作方）按项目实施**，不是每家公司从零定制，也不是让客户员工自助搭建。平台不内置“供应链”“生产”这类行业模板；每个行业的差别全部落在**项目里建的本体（对象、关系、函数、行动）**上，靠厂商的一套固定流程快速做出来。

## 对方怎么做的

**1. 产品层面：一套通用底座，不分行业**（第三方厂商自述）
- 白皮书第 4 页把 AbutionGraph 定位成通用的“图 + 时序 + 向量”一体数据库；第 8 页架构图的数据源是 ERP / WMS / TMS / IoT，应用层是监控大屏、风险预警、推演、优化建议、报表——全是通用能力，没有按行业分产品。
- README：“为 AI 应用开发提供一套通用的基建模式，复用于任意的行业场景，快速 toB/toG 项目交付。”

**2. 行业差别在哪里体现：本体 = 计算公式（函数）+ 上下游关系（图）+ 异常触发（行动）**（第三方厂商自述）
- 第 14 页烟草制丝案例写得最直白：“工业场景每个环节都有很多计算公式（函数），且具有上下游联动后果（图谱），当某环节数据异常（监控）时触发报警或参数调优（行动）”。
- 第 10 页给出的建模方式是**写代码**定义 Schema（`.entity(...).property(..., Agg.Sum())...action(...)`），每个属性带聚合函数，行动挂在实体上。
- 第 21 页天然气案例展示了固定套路：① 搭基础静态框架图谱 → ② 流式数据导入 → ③ 时序函数计算 → ④ 监控预警。

**3. 交付流程：一条固定流水线，一个流程就是一个应用**（第三方厂商自述）
- README：“需求分析 → 数据源表 → 数据处理 → 子图建模 → 本体库 → 本体应用”，“一个流程 = 一个软件”，画布里有 AI 助手辅助生成配置和代码。
- 第 7 页：“1 人实施 / 可单兵作战”，“需求变更时只需调整本体模型”。

**4. 谁来搭：厂商卖的是“项目”，不是自助工具**（第三方厂商自述）
- 第 11 页：“我们卖软件，更多是卖时间——以标准化的架构快速制造出客户需要的系统”；痛点对应的解法里写着“套模板快速原型验证”“函数式编程二开（二次开发）”“粘性开发持续迭代”。
- 第 31 页报价体系全部是项目制：试点验证 ¥15 万起/项目/月（含**业务诊断、核心本体构建、POC 系统开发**）；拓展推广 ¥30 万起/年/项目 + 20% 项目盈利；深度应用 ¥99.8 万起（私有平台定制）。本体是厂商帮客户建的。
- 第 13 页工业互联网案例：同一个基础服务平台上，按行业（电子信息 / 航空 / 钢铁）各挂一个子平台，每个子平台里都是“供应链管理、质量监测优化、其他”——**通用底座 + 行业子平台**的分层。
- 案例（第 12–28 页）覆盖公安、烟草、生物、电信、天然气、车险、电网等，几乎都是“为某客户建的平台”，界面风格各不相同（大屏、手机端、业务系统），说明前端也按项目做。

**5. 例外：客户内部人员能用到的部分**（第三方厂商自述）
- README：智能体“配置完成即可独立运行，业务人员不必进入后台”；孪生应用可“拖拽搭建”。即业务人员是**使用者**，搭建者仍是懂本体的实施人员（厂商、合作伙伴或客户 IT）。

**6. 唯一接近供应链决策的展示：README「六、推演沙盘」配图**（第三方厂商自述 + 截图，原件 `evidence/ontoflow-github-readme-2026-10-23/sandbox_supply_chain_propagation.png`）
- 白皮书第 12–29 页的行业案例里**没有供应链缺料或订单决策**：公安、烟草、生物、电信、天然气、车险、电网等案例讲的都是图谱、时序计算和监控大屏。第 13 页只在工业互联网的子平台列表里写了"供应链管理"四个字；第 24 页是最接近的数据形态（烟草零售的订购量、需求量、库存量周/月销量预测），但没有决策环节。
- 推演沙盘截图里的场景：**供应商 SUP006 断供后，风险怎么从 SUP006 传到工厂 FAC007，再传到订单 ORD012**。画面包括：
  - 顶部状态栏：风险 TOP 3 供应商带评分（非洲稀土矿业 0.64、中东石化供应 0.59、南亚化工原料 0.41），"时机感知"提示"宜在 Tick #0~#12 窗口内行动，避免错过 deadline"，可执行行动 7/7，检查点和场景 KPI
  - 中间：因果链视图（SimAction → SimEvent → SimEffect，边类型 PRODUCES / MODIFIES / CAUSES）、传播过程、未来事件、规则系统
  - 右侧：AI 推演指挥台，用户问"解释风险如何从 SUP006 传到 FAC007 再传到 ORD012"，Agent 一边调用工具一边分步回答；还有"行动审计"标签
- 截图时刻是 Tick 0，"本 Tick 影响"里实体、关系、规则都是 0，Agent 回答停在"首先，查询当前世界状态"并重复了几遍。**截图里看不到任何算出来的影响数字或推荐结论**（本项目推断）。

## 和我们现状的差距（本项目推断）

- 我们同样是“通用平台 + 每个场景一份示例应用/数据”（如 MRPSpeed、Machinery demo），思路一致。
- 差别在于他们把**交付流水线**固定成一条可视化流程，并在每一步用 AI 辅助；我们的场景搭建更多靠脚本（如 `backend/scripts/build_mrpspeed_demo.py`）。
- 他们把行业逻辑放进本体的**函数和行动**（数据变化时自动重算、触发告警）；我们的派生指标和告警分散在查询和应用配置里。

## 可以借鉴

- **不做行业模板，做“建模套路”**（本体建模 / 场景搭建，中）：静态框架 → 数据导入 → 派生计算 → 监控预警，这四步可以作为我们新场景上手的标准清单。
- **把场景搭建脚本化流程沉淀成平台里的固定步骤**（数据摄取 → 建模 → 应用，低-中）：让新场景不必写一次性脚本。
- **定位上分清两类用户**：搭建者（懂本体）和使用者（业务人员），界面分开设计。

## 不该照搬 / 存疑

- 白皮书是销售材料：“开发效率 10 倍”“查询 50 倍”“数据合规 100%”没有给出测试条件，不作为依据。
- 和 Palantir 的对比表（第 9 页）是厂商自评，和官方资料冲突时以官方为准。
- “1 人实施”只说明他们的实施人员熟练，不说明客户员工能自助搭建；我们不应据此假设业务人员能独立建本体。
