# 数据导入、时序、常规与多模态操作说明

> 本文对应当前研究原型的本地演示环境。它不代表生产部署、压力测试或工业现场数据的结论。

## 1. 当前系统在做什么

系统把原始数据转换成“本体结构 + 本体实例 + 可追溯证据”：

```text
数据文件 → Dataset/Version → Pipeline 或 ConstructionRun → 本体映射
        → FalkorDB 实例节点/关系 → Graph 页面、时间快照、来源证据
```

本体是允许出现的类型和关系（例如 `Equipment`、`Observation`、`OBSERVED_ON`）；知识图谱是按这些规则写入的具体设备、读数、事件及边。当前所有新实例图均按 ontology 隔离写入 FalkorDB。

## 2. 服务与数据位置

| 内容 | 位置/服务 | 作用 |
|---|---|---|
| BTS Site B 原始演示 | `backend/data/bts_demo/observations.csv`、`Site_B.ttl`、`manifest.json` | 时序数据和 Brick 元数据；不把 `cycle` 猜成日期 |
| C-MAPSS FD001 Dataset/Curated | MinIO `raw-datasets`（版本 URI 记录在 PostgreSQL） | 常规 CSV 的原始版本和 Pipeline 输出 |
| Dataset、Pipeline、Ontology、Run、EvidenceRef | PostgreSQL | 元数据、状态、指标、来源行/媒体定位 |
| 实例节点和关系 | FalkorDB，图名 `nano_<ontology_uuid>` | Graph 页面实例、关系、时间属性和幂等写入 |
| 本地模型 | Ollama `qwen3.5:0.8b` | 文本映射、质量检查和审查解释 |
| 多模态模型 | PostgreSQL 加密 ModelConfig 中的 MiniMax M3 | 图片/PDF 等证据提取；密钥不写入仓库或响应 |

## 3. 启动和登录

在运行工作树执行：

```bash
docker compose -f docker-compose.v2.yml up -d
open http://127.0.0.1:5173/
```

默认开发账号是 `admin`，密码是 `admin123`。首次使用后可在“设置”修改密码。健康检查：

```bash
curl http://127.0.0.1:8000/health
```

必须看到 `db`、`falkordb`、`minio` 为 `ok`；这只证明服务可连接，不等于某个构建任务已完成。

## 4. 时序数据：BTS Site B → Brick → FalkorDB

### 页面操作

1. 左侧进入 **数据管理 → 时序数据**。
2. 在“选择数据”确认 `BTS Site B`，检查预览表、流数量、输入行数和时间范围。
3. 在“配置时间语义与实体列”选择 `instant`，实体列填 `stream_id`，时间列填 `event_time`。如果使用其他数据，可改为 `ordinal`（如 cycle）或 `interval`（如 valid_from/valid_to）。
4. 在“本体映射与执行”检查 Brick 类别标签，点击 **创建时序本体构建任务**。
5. 等待 Run 变为“已完成”，核对输入行、规范化行、节点、边和问题数。
6. 在结果区域使用时间轴滑块、播放/暂停、快照时间输入框和 **查看当前快照**。
7. 输入“从/到”两个时间，点击 **比较两个时刻**，查看新增/移除节点和边。
8. 点击 **打开 Schema / 实例图**，在 Ontology 的 Graph 标签页切换 Schema/实例，按类型和时间筛选；节点详情中的 `event_time`、`event_seq`、原始值和 EvidenceRef 是来源证据。

### 后端语义

- `Building`、`Zone`、`Equipment`、`Point`、`Observation`、`AnomalyEvent` 是类型；实例按稳定 ID 写入。
- `event_time` 表示真实时间点；`event_seq` 只表示顺序时间；`valid_from/valid_to` 表示关系有效区间。
- 非法、缺失或逆序时间进入问题清单，系统不会自动猜日期。
- 重复运行使用 FalkorDB `MERGE`，节点和边数量不会持续增长。

常用接口：

```text
GET /api/v2/temporal/catalog
POST /api/v2/ontologies/{ontology_id}/temporal/runs
GET /api/v2/ontologies/{ontology_id}/temporal/snapshot
GET /api/v2/ontologies/{ontology_id}/temporal/timeline
GET /api/v2/ontologies/{ontology_id}/temporal/diff
GET /api/v2/ontologies/{ontology_id}/temporal/growth
```

## 5. 常规数据：C-MAPSS → Dataset → Pipeline → Curated → 本体实例

### 数据在哪里

C-MAPSS 的原始 CSV 和 Curated 内容已进入 MinIO；Dataset、版本、Pipeline、审核和映射元数据在 PostgreSQL；写入后的 `Equipment`、`SensorReading` 和关系在 C-MAPSS 对应 FalkorDB 图中。不要直接修改数据库行，页面和 API 会维护这些引用。

### 导入新文件

1. 进入 **数据管理 → 常规数据**。
2. 点击右上角 **导入文件**，或进入“数据源与数据集”。
3. 选择 CSV/XLSX/JSON 并上传。系统创建 Dataset 和 Dataset Version，文件对象存入 MinIO。
4. 展开 Dataset 查看来源、版本、行数、Schema 和预览。
5. 进入 **Pipeline 转换**，打开已有 Pipeline 或创建新 Pipeline。
6. 依次点击 **校验**、**运行**，等待输出 Curated Dataset。
7. 在 **Curated 数据**查看审核状态；只有 Curated 完成映射后才会产生本体实例图。
8. 打开目标 Ontology → **Graph → 数据实例**，查看具体设备、读数和关系，而不是只看 Schema。

删除 Dataset 需要管理员权限。若仍被 Pipeline、Run 或 Mapping 引用，接口会返回引用清单并拒绝删除；请先解除引用，不要用 SQL 强制删除。

## 6. 多模态：MVTec AD 2 + MiniMax M3

MVTec AD 2 是公开工业缺陷图片基准，官方页面提供超过 8,000 张图片，下载需要完成许可/表单，并遵守 CC BY-NC-SA 4.0：<https://www.mvtec.com/research-teaching/datasets/mvtec-ad-2>。官方图片不提交到 Git。

### 安装样例

下载官方压缩包后，在后端容器可访问的路径运行：

```bash
docker cp scripts/import_mvtec_ad2.py nano-ontology-next-backend-1:/app/import_mvtec_ad2.py
docker cp /path/to/mvtec_ad_2.zip nano-ontology-next-backend-1:/tmp/mvtec_ad_2.zip
docker exec -w /app nano-ontology-next-backend-1 \
  python /app/import_mvtec_ad2.py --input /tmp/mvtec_ad_2.zip
```

脚本最多导入 32 张图，每个场景最多 2 张正常图和 2 张异常图；同时创建 `MVTec AD 2 视觉检测样例` Dataset 和 `MVTec AD 2 视觉检测本体`。未安装时页面明确显示“样例尚未安装”，不会伪造图片。

### 页面操作

1. 进入 **数据管理 → 多模态数据**。
2. 在“选择或上传媒体”选择 MVTec 样例，或选择 PNG/JPG/WEBP/PDF/DOCX/MP4/MOV 上传。上传只负责登记原文件和 `MediaItem`。
3. 选择目标本体，确认右上角 **MiniMax M3：可用**。状态接口只返回配置状态和模型名，不返回 Key。
4. 点击 **创建多模态构建任务**，等待 Run 进度和媒体成功/失败计数。
5. 点击媒体行的 **查看证据**，查看 MiniMax 返回文本、文件名、对象 URI、提取器和状态。
6. Run 完成后点击 **打开实例图**。图中包含 `MediaAsset`、`ExtractedFragment`、`InspectionEvent`，异常标签来自官方归档路径/元数据；M3 只生成可追溯描述。

MiniMax M3 的配置通过 `MINIMAX_API_KEY` 启动环境完成模型列表校验后加密保存。请求使用 `max_completion_tokens`、adaptive thinking 和 `reasoning_split`，不会发送其不兼容的 `seed` 或 JSON response format。没有明确 ID、文件元数据或可定位文本证据时，模型不能直接创建业务关系；视频本阶段只登记，不声称理解视频语义。

## 7. 清理与恢复

清理脚本只针对运行库，不删除仓库 `test_data/` 和 BTS 源文件。执行前必须备份：

```bash
docker cp scripts/cleanup_demo_runtime.py nano-ontology-next-backend-1:/app/cleanup_demo_runtime.py
docker exec -w /app nano-ontology-next-backend-1 \
  python cleanup_demo_runtime.py --dry-run
```

dry-run 会列出将保留/删除的本体、Dataset、Pipeline、Run 和图名。正式执行需要显式确认：

```bash
docker exec -w /app nano-ontology-next-backend-1 \
  python cleanup_demo_runtime.py --apply --confirm BTS-CMAPSS
```

当前备份位于 `.runtime_backups/2026-09-01-before-cleanup/`，包括 PostgreSQL custom dump、FalkorDB 图清单、MinIO 对象清单和元数据清单。恢复时先停止写入，再使用 `pg_restore` 恢复 PostgreSQL；MinIO 对象按清单从备份恢复，FalkorDB 图由对应构建任务幂等重建。

## 8. 老师演示顺序（约 5 分钟）

1. 概览确认服务状态和数据源数量。
2. 时序数据页面预览 BTS，展示 `instant` 时间配置并创建 Run。
3. 打开 Schema/实例图，说明 Brick 类型和真实 Observation 节点的区别。
4. 拖动时间轴，展示快照节点数量变化；输入两个时刻展示 diff。
5. 点击节点展示原始行和 EvidenceRef。
6. 常规数据页面打开 C-MAPSS Dataset → Pipeline → Curated → 实例图，说明表格到图谱链路。
7. 多模态页面展示 M3 状态；若已安装 MVTec，运行最多 32 张图片并展示提取文本和证据。若未下载官方数据，明确说“样例尚未安装”，不要把占位数据当成结果。

## 9. 常见问题

- **登录后又回到登录页**：检查浏览器是否保留 token，重新登录并确认 `GET /api/v1/auth/profile` 返回用户。
- **Ollama 模型不可见**：确认 `curl http://127.0.0.1:11434/api/tags` 有 `qwen3.5:0.8b`，再在“模型”页面刷新。
- **MiniMax 显示未配置**：检查后端进程是否配置了 `MINIMAX_API_KEY`，并确认 `/api/v2/multimodal/status` 的 `available`；不要把 Key 写进代码或文档。
- **FalkorDB 未连接**：检查 `/health` 的 `falkordb`，不要把 SQLite 回退数据称为 FalkorDB 图。
- **时序数据为空**：确认 Run 已完成并选择正确的时间列；非法时间只会进入问题清单，不会被猜测修复。
- **多模态 Run 失败**：先查看 Run 的错误和媒体状态；失败会保留原媒体和失败 Fragment，不创建模型猜测的关系。
